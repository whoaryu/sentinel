Project Overview

The Sentinel Implementation Plan

The core insight: the LLM is a translator, not an executor. It emits a typed Vec<Action>. A separate Rust policy engine validates it. A separate Rust execution engine runs it with least-privilege elevation. The AI never touches the system directly — that boundary is the entire project.

Five Components

Frontend
React — input field, renders the plan as a diff/checklist, approve/reject button, streams live status over WebSocket, audit log viewer.
Orchestrator
Rust + Axum — the API server. Owns the session state machine: Drafting → PendingApproval → Approved → Executing → Done/Failed. Calls the other four components.
LLM Layer
Claude/GPT-4o function calling — NL → strictly-typed ActionPlan JSON. Free text is never trusted as an instruction; the model only produces structured, enumerable data.
Policy Engine
Pure Rust — takes an Action, returns Allow | Deny(reason) | RequireExtraConfirmation. Synchronous, zero IO, trivially unit-testable. The most interview-worthy component.
Execution Engine
Rust trait + OS backends — one PrivilegedExecutor trait with Windows, Linux, macOS impls behind #[cfg(target_os)]. This is where UAC / Polkit / AuthorizationServices live.
Architecture

The Action Enum — Get This Right First

The most critical design decision. A closed enum means the policy engine can pattern-match exhaustively, every variant is independently testable, and the UI can render a human-readable diff. Never let the model emit raw shell commands — that's the whole point.

// sentinel-core/src/action.rs
#[derive(Serialize, Deserialize, Debug, Clone)]
#[serde(tag = "type")]
pub enum Action {
    DeleteFile {
        path: PathBuf,
        reason: String,           // LLM must justify every action
    },
    DeleteFilesMatching {
        root: PathBuf,
        older_than_days: Option<u32>,
        pattern: Option<String>,
        reason: String,
    },
    MoveFile      { from: PathBuf, to: PathBuf, reason: String },
    ChangePermissions { path: PathBuf, mode: PermissionSpec, reason: String },
    KillProcess   { pid_or_name: ProcessTarget, reason: String },
    CompressDirectory { path: PathBuf, output: PathBuf, reason: String },
    FindLargeFiles { root: PathBuf, min_size_mb: u64 }, // read-only — no policy needed

    // Deliberately NOT here: RunShellCommand(String)
    // "I treated the LLM as a translator into a closed vocabulary"
}

pub enum PolicyDecision {
    Allow,
    Deny(String),
    RequireExtraConfirmation(String),
}
Interview line
The closed enum means Rust's exhaustive match forces you to handle every action in the policy engine. You literally cannot ship a new action without a policy decision. That's not a cute trick — it's the safety property made structural.

Tech Stack

What to Actually Use

Core
Rust + Cargo workspaces
Monorepo: sentinel-core, sentinel-policy, sentinel-exec, sentinel-api as separate crates.
API Server
Axum
Minimal, async, great WebSocket support. Add tower-http for CORS and tracing.
Frontend
React + Vite
Vite's dev server proxies to Axum seamlessly. Use Tailwind for speed — you're building a tool, not a marketing site.
LLM
Claude claude-sonnet-4-5 or GPT-4o
Use structured outputs / JSON schema mode. Model the Action enum as a JSON schema — the model fills it in.
Serialization
serde + serde_json
The Action enum crosses every boundary — Rust↔LLM, Rust↔UI. serde is the project's backbone.
OS (Windows)
windows-rs
First-party Microsoft bindings. Use ShellExecuteW("runas") for UAC, SetNamedSecurityInfoW for ACLs.
OS (Linux)
nix crate
POSIX wrappers over chmod, chown, signals. Elevation via pkexec (Polkit) — GUI-friendly prompt.
Audit Log
SQLite via sqlx
Local append-only log. Async, compile-time query checking, no server needed. Add a CHECK trigger to prevent updates.
Testing
Rust built-in + proptest
Policy engine is pure — property-test it with proptest. Generate random Actions and assert policy invariants hold.
Build for one OS first
Implement fully on whatever you dev on daily. Stub the other backends with unimplemented!("Linux backend — see ARCHITECTURE.md"). "Designed for 3 platforms, fully implemented on Windows + Linux, macOS stubbed with documented approach" is honest and strong. A shallow broken 3-OS impl is worse than one solid one.
Build Sequence

Five Phases — Work Front-to-Back Within Each

Each phase is independently shippable and testable. Never start a new phase with a broken previous one. The test suite is your progress tracker.

1
Core Schema + Policy Engine
2–3 days
▶
Goal
Write and fully unit-test the two most important files in the project: the Action enum and the policy engine. No LLM, no UI, no real execution yet — just types and logic.
  • 1
    Create Cargo workspace: sentinel-core (shared types), sentinel-policy (depends on core), sentinel-exec, sentinel-api. Add serde + uuid + chrono to core from day one — every other crate uses them.
  • 2
    Define the full Action enum in sentinel-core/src/action.rs. Add every variant you plan to support. Derive Serialize, Deserialize, Debug, Clone. Write the ActionPlan struct too. This file is the contract everything else implements against. lock this early
  • 3
    Write the policy engine in sentinel-policy/src/lib.rs. A PolicyEngine::evaluate(&Action) → PolicyDecision function with match arms for every variant. Start with simple rules: deny paths outside $HOME, deny deleting system directories, deny killing PIDs under 100.
  • 4
    Write 20+ unit tests for the policy engine. Test the allow cases, deny cases, and the "requires extra confirmation" cases explicitly. This is your safety story — make it airtight. test-heavy
  • 5
    Write a hardcoded integration test with a Vec<Action> that includes one action that should be blocked. Assert the policy engine catches it. This becomes your demo — run it in the interview.
2
Execution Engine + Audit Log
3–4 days
▶
Goal
Implement 3 action types (DeleteFilesMatching, ChangePermissions, KillProcess) on your development OS only. Ship the append-only SQLite audit log.
  • 1
    Define the PrivilegedExecutor trait in sentinel-exec. Every OS backend implements this one trait. Add a DryRunExecutor that logs what would happen but does nothing — this is your first implementation and stays useful forever. safe default
  • 2
    Implement elevation. On Linux: spawn a child process under pkexec, pass the action as JSON over stdin, read the result from stdout. On Windows: ShellExecuteW("runas") with a minimal helper binary. The key pattern: elevate per-batch, not per-app-launch.
  • 3
    Implement the 3 action types behind your OS backend. Start with DeleteFilesMatching — it's the most common use case and tests your path traversal code thoroughly. Add real error handling: can't delete a locked file, path doesn't exist, permission denied despite elevation.
  • 4
    Create the SQLite audit log with sqlx. Schema: plan_id, action_type, path, status, timestamp, error_msg. Add a trigger that prevents UPDATE/DELETE on the table — append-only is a structural guarantee, not a convention. audit trail
  • 5
    Write a CLI driver (sentinel-cli binary) that takes a hardcoded ActionPlan, runs it through the policy engine, prints "Proceed? [y/N]", then executes on approval. This is your full pipeline working end-to-end before any LLM or UI exists.
3
LLM Integration
2–3 days
▶
Goal
Wire NL → typed ActionPlan via function-calling. Test via curl and your CLI driver — no UI needed yet.
  • 1
    Convert your Action enum to a JSON Schema. Use schemars crate — derive JsonSchema on Action and call schema_for!(ActionPlan). That schema becomes your function-calling tool definition. This is the cleanest approach: your types generate the schema, not the other way around. single source of truth
  • 2
    Write the system prompt carefully. Tell the model: it's a translator into a closed action vocabulary, it must justify every action with a reason field, it must return NeedsClarification instead of guessing when the request is ambiguous, and it must estimate impact (file count, total size). Include a few examples in the prompt.
  • 3
    Add the NeedsClarification response path. If the model returns this instead of an ActionPlan, the orchestrator sends the clarifying question back to the UI. This handles "clean up my downloads" (by age? by type? what threshold?) gracefully. moderate effort, high payoff
  • 4
    Add the Axum API server. Two endpoints to start: POST /api/plan (NL → ActionPlan, runs policy, returns plan with decisions) and POST /api/plan/:id/execute (executes an approved plan, streams progress via WebSocket). Store plans in memory first; persist to SQLite later.
  • 5
    Test with curl. Post "kill any process using more than 90% CPU" and see what the model returns. Post "delete system32" and confirm the policy engine blocks it. Have these curl commands in a test-cases.sh file — they become your demo script.
4
React Frontend
3–4 days
▶
Goal
A working UI: text input → plan review with approve/reject → live WebSocket execution stream. Three screens, built incrementally.
  • 1
    Screen 1 — Input. A single text field with a submit button. Nothing fancy. Send to POST /api/plan, show a loading state. Configure Vite to proxy /api/* to your Axum server on port 3001. start here
  • 2
    Screen 2 — Plan Review. This is the project's most important screen. Render each action as a card with: the action type as a badge, the path/target, the LLM's reason, the policy decision (green Allow / red Deny / yellow Needs Confirmation), and the estimated impact. A big "Approve Plan" button and a "Cancel" button. Make blocked actions visually unmistakable.
  • 3
    Screen 3 — Live Execution. Open a WebSocket to /ws/plan/:id on approve. Render each action as a row that transitions through pending → running → ✓ done / ✗ failed. The running state should have a subtle animation. Show a final summary: "12 files deleted, 340MB freed, 0 errors."
  • 4
    Add the Audit Log viewer as a tab or sidebar route. List past plans: timestamp, original request, N actions, status, expand to see each action's result. This is cheap since the data already exists in SQLite — just add a GET /api/audit endpoint. big visual payoff
  • 5
    Dry-run mode toggle. A toggle in the header that sends dry_run: true with the execute request. The execution engine routes to DryRunExecutor instead of the real one. Show "Simulation" badge on the results. This is your safest demo default.
5
Demo Polish + README
1–2 days
▶
Do not skip this phase
A well-polished 90-second demo matters as much as the code. The README is the first thing a recruiter or interviewer reads. This phase has the highest ROI of any time you'll spend.
  • 1
    Script your demo in advance. Two scenarios: (1) normal happy-path — "move all PDFs from Downloads to Documents/PDFs", show review screen, approve, watch it execute live. (2) blocked request — "delete everything in /tmp including system files", show policy engine catching it and displaying the deny reason.
  • 2
    Write the README architecture section first — not last. It forces you to explain the design clearly, which reveals any gaps. Include: a 2-sentence pitch, an architecture diagram (ASCII or Mermaid), the Action enum (yes, paste it — it's that important), and the 5-component list with one line each.
  • 3
    Write a "Future Work" section — scheduled tasks, multi-user approval, undo for reversible actions, voice input via Whisper. A thoughtful future-work section signals you designed beyond MVP scope. It also gives interviewers easy follow-up questions you're prepared for.
  • 4
    Add blast-radius caps to the policy engine. A rule like "no single plan may delete more than 50 files or 1GB without an extra confirmation step." One additional match arm, five lines of code, but it's a real safety property and a great talking point.
Making It Better

Features That Actually Move the Needle

Ranked by interview-value-per-hour-of-work. Stop after item 3 unless you have extra time.

Do these — they're essentially free

  • Hardcoded blocked scenario in the demo. A policy rule "never touch anything outside $HOME" and a test input that violates it. Zero engineering, maximum persuasion.
  • Require reason on every Action. Forces the LLM to justify every action. Renders as a quote in the review UI. Signals you thought about accountability, not just capability.
  • ImpactSummary on every plan. "12 files, 340MB, oldest from 2019" shown before the user approves. The LLM estimates this; you re-calculate it in Rust to verify. The discrepancy is worth checking.
  • Reversibility tags. Mark each action in the UI as ✓ Reversible (Move, Compress) or ✗ Irreversible (Delete, Kill). Purely visual, but frames your safety thinking immediately.

Worth an afternoon each

  • Soft-delete instead of hard-delete. Route all DeleteFile actions through a .sentinel-trash/ staging directory with a 7-day retention window. Adds undo, prevents accidents, and is a real safety pattern — not fake. Show the retention logic in your README.
  • Ambiguity detection. If the LLM returns NeedsClarification, the UI shows the model's question and lets the user refine their request inline. Demonstrates you handled the unhappy path thoughtfully.
  • Property-test the policy engine with proptest. Generate random Actions and assert that "actions outside HOME are always denied" and "actions with path traversal (../) are always denied." Shows testing maturity.

Stretch goals (only if MVP is rock-solid)

  • Voice input via Whisper API. Browser mic → POST /api/transcribe → same NL pipeline. Adds a show-stopping demo moment for very low integration effort. Don't build STT yourself — use the API.
  • Scheduled recurring plans. "Every Sunday, clean up Downloads older than 90 days." Interesting because it forces you to design "who approves an automated privileged action" — a real problem without an obvious answer. Even a half-built version is a great talking point.
Making It Easier

Practical Shortcuts That Don't Cut Corners

  • Start with the DryRunExecutor and never remove it. 80% of your development time runs in dry-run mode. You can build and test the entire pipeline — schema, policy engine, LLM integration, frontend — without touching your filesystem once. Real execution is only the final integration step.
  • Use schemars to generate your LLM tool definition. Don't hand-write a JSON schema for the Action enum. #[derive(JsonSchema)] + schema_for!(ActionPlan) gives you a perfectly accurate schema from your Rust types automatically. The model's output then matches your types structurally.
  • Build the frontend against mock data first. Hardcode a ActionPlan JSON file in the React project. Build all three screens to full polish against it before writing a single API call. Then swap the mock for real API calls in one pass.
  • Keep the CLI driver. Every time you add a new feature to the Rust core, test it with the CLI driver first before testing it through the full stack. cargo run --bin sentinel-cli -- "clean up downloads" is 10× faster to iterate on than running the full UI.
  • Use cargo-watch for the Rust server and Vite HMR for React. cargo watch -x "run --bin sentinel-api" + Vite dev server = instant feedback loop. Set these up on day one.
  • Pick one OS and go deep, not three and go shallow. Implement a real, fully working elevation flow on your development machine. Leave the other two as documented stubs. One correct implementation is far more impressive than three broken ones.
  • Use thiserror from the start. Define a project-wide SentinelError enum with #[derive(thiserror::Error)]. Consistent error types across every crate makes the API layer's error handling trivial and makes your code look professionally structured.
  • Store the LLM prompt in a file, not in source code. Put your system prompt in prompts/plan_system.md and load it at startup. This lets you iterate on prompt engineering without recompiling, and shows separation of concerns to anyone reading the repo.
Interview Prep

Lines Worth Rehearsing

Q: Why not just let the LLM run shell commands?
I treated the LLM as a translator into a closed, typed vocabulary — not as an execution engine. A closed enum means Rust's exhaustive match forces the policy engine to handle every possible action. You literally cannot ship a new action type without a corresponding policy decision. That's a structural safety guarantee, not a convention.
Q: How does the OS elevation work?
I elevate per-batch, not per-app-launch. When the user approves a plan, the execution engine spawns a short-lived helper process under pkexec (Linux) or ShellExecuteW with "runas" (Windows), passes the approved action set over a pipe as JSON, and reads results back. The orchestrator itself never runs elevated — only the helper, only for that specific set of actions, only after the policy engine has signed off.
Q: How do you test something with privileged OS operations?
The policy engine is pure and synchronous — no IO, no elevation, trivially unit-tested. The execution layer has a DryRunExecutor implementing the same trait that logs what would happen without doing it. I can test the entire pipeline — LLM translation, policy decisions, execution plan — without touching the filesystem at all. Real execution is only the final integration step.
Q: How do you handle a cross-platform codebase?
The policy engine and orchestrator have zero OS-specific code. Only the execution engine varies, behind one PrivilegedExecutor trait. Adding a fourth platform means writing one new impl PrivilegedExecutor and touching nothing else. I implemented fully on Linux, have Windows working for the core actions, and macOS is stubbed with the approach documented in ARCHITECTURE.md.
Q: What's the audit log for, and why is it append-only?
The audit log records every plan, every policy decision, and every execution result. It's append-only structurally — I added a database trigger that rejects any UPDATE or DELETE. This isn't a convention; the database enforces it. So even if the execution engine had a bug or a compromised path, you have a complete tamper-evident record of what ran and when.
