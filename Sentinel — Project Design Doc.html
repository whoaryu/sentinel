Sentinel — Elevated Task Automation Tool with Natural-Language Interface

One-line pitch: A safety-first system automation tool where an LLM translates natural language (text or voice) into an explicit, reviewable action plan, and a Rust core independently validates and executes privileged OS operations — the AI never touches the system directly.

Target audience for this doc: yourself, mid-build, and anyone (interviewer, collaborator) trying to understand the architecture quickly.

1. Why this project exists (the pitch, in one paragraph)

Most "AI does X on your computer" demos let the model execute freely — that's a security nightmare and shows the builder didn't think about failure modes. Sentinel is built around one hard rule: the LLM only ever produces structured, typed data (an "Action Plan"). It never runs a command, touches a file, or spawns a process. A separate Rust policy engine validates every action against explicit rules before a separate Rust execution engine (running with least-privilege elevation) carries it out — and every step is logged to an audit trail. The interesting engineering is entirely in that boundary and everything downstream of it.

2. High-level architecture

┌─────────────┐      ┌───────────────┐      ┌──────────────────┐      ┌──────────────────┐
│  Frontend    │─────▶│  Orchestrator  │─────▶│   LLM (planning)  │      │                    │
│  (React)     │      │  (Rust API)    │      │   NL → Action[]   │      │                    │
│  text/voice  │◀─────│  WebSocket +   │◀─────┴──────────────────┘      │                    │
└─────────────┘      │  REST          │                                 │                    │
                       │                │──────▶ Policy Engine ─────────▶│  Execution Engine  │
                       │                │        (validate)              │  (privileged, per-  │
                       │                │◀───────────────────────────────│  OS backend)       │
                       │                │                                 │                    │
                       │                │──────▶ Audit Log (append-only) ▶│                    │
                       └───────────────┘                                 └──────────────────┘

Five components, each independently testable:

  1. Frontend (React) — captures input (text/voice), renders the proposed plan as a diff/checklist, shows approve/reject, streams live execution status, shows audit history.
  2. Orchestrator (Rust, e.g. Axum) — the API layer. Owns the WebSocket connection, calls the LLM, calls the policy engine, calls the execution engine, writes to the audit log. This is the "glue" service but still meaningfully engineered (state machine per session: Drafting → PendingApproval → Approved → Executing → Completed/Failed).
  3. LLM planning layer — takes raw NL, returns a strictly-typed JSON Vec<Action> via function-calling / JSON schema mode. No free text is ever trusted as an instruction.
  4. Policy engine (Rust) — pure, synchronous, easily unit-tested. Takes an Action, returns Allow | Deny(reason) | RequireExtraConfirmation(reason).
  5. Execution engine (Rust, OS-specific backends) — actually performs privileged operations. This is where OS-specific code lives (see Section 4).

3. The Action Plan contract (the core abstraction)

This is the single most important design decision in the whole project — get this right first.

#[derive(Serialize, Deserialize, Debug, Clone)]
#[serde(tag = "type")]
pub enum Action {
    DeleteFile { path: PathBuf, reason: String },
    DeleteFilesMatching { root: PathBuf, older_than_days: Option<u32>, pattern: Option<String>, reason: String },
    MoveFile { from: PathBuf, to: PathBuf, reason: String },
    ChangePermissions { path: PathBuf, mode: PermissionSpec, reason: String },
    KillProcess { pid_or_name: ProcessTarget, reason: String },
    CompressDirectory { path: PathBuf, output: PathBuf, reason: String },
    // deliberately NOT: RunShellCommand(String) — never let the model emit raw shell
}

#[derive(Serialize, Deserialize, Debug, Clone)]
pub struct ActionPlan {
    pub id: Uuid,
    pub original_request: String,       // what the user typed/said
    pub actions: Vec<Action>,
    pub estimated_impact: ImpactSummary, // e.g. "12 files, 340MB, oldest from 2019"
    pub created_at: DateTime<Utc>,
}

Why a closed enum and not "let the LLM write a script":

  • Every possible action is enumerable, testable, and independently safe to implement.
  • The policy engine can pattern-match exhaustively (Rust will force you to handle every variant).
  • You can render a readable diff in the UI — "delete 12 files in ~/Downloads older than 90 days" is renderable; an arbitrary shell script is not.
  • This is your strongest interview line: "I treated the LLM as a translator into a closed, typed vocabulary — not as an execution engine."

4. How each OS is handled

The policy engine and orchestrator are OS-agnostic. Only the execution engine has per-OS backends, behind a single trait:

trait PrivilegedExecutor {
    fn delete_file(&self, path: &Path) -> Result<ExecutionResult, ExecError>;
    fn change_permissions(&self, path: &Path, mode: &PermissionSpec) -> Result<ExecutionResult, ExecError>;
    fn kill_process(&self, target: &ProcessTarget) -> Result<ExecutionResult, ExecError>;
    fn elevate(&self) -> Result<ElevationToken, ExecError>;
}

Three implementations, selected via #[cfg(target_os = "...")], matching your earlier OS-integration practice work directly.

Windows

  • Elevation: ShellExecuteW with "runas" verb to spawn an elevated helper process for a single action — never run the whole app elevated. UAC prompt appears per privileged batch, not per app launch.
  • Permissions: Windows ACLs via windows-rs bindings (SetNamedSecurityInfoW) rather than trying to force POSIX-style chmod semantics.
  • Process management: OpenProcess + TerminateProcess via Win32 API, process listing via CreateToolhelp32Snapshot.
  • Registry (stretch, see Section 6): RegOpenKeyExW/RegSetValueExW — only if you add registry actions later; keep it out of MVP.
  • Secure secrets/config (if needed): DPAPI (CryptProtectData), same pattern as your vault project — reusable code.

Linux

  • Elevation: pkexec (Polkit) for GUI-friendly elevation prompts, or sudo with a clearly scoped policy file if running headless/server-side. Spawn a short-lived elevated child process per action, communicate result back over a pipe.
  • Permissions: direct POSIX chmod/chown via nix crate, or raw syscalls if you want to flex — either is defensible.
  • Process management: read /proc/[pid]/ for process listing (no special API needed), send SIGTERM/SIGKILL via nix::sys::signal.
  • Config files (stretch): plain files, permissions-protected — no registry equivalent, which is worth explicitly noting in your README as a platform difference.

macOS

  • Elevation: AuthorizationExecuteWithPrivileges (deprecated but still common) or a proper SMJobBless-style privileged helper tool (more correct, more work — good stretch goal if you want to show you know the "right" way vs the "quick" way).
  • Permissions: POSIX permissions same as Linux, but be aware of extended attributes (xattr) and TCC (Transparency, Consent, Control) — macOS will silently block access to protected folders (Downloads, Desktop) unless the app is granted permission. This is a great thing to document as a discovered constraint — shows real hands-on exposure.
  • Process management: same POSIX signal APIs as Linux.
  • plist editing (stretch): plist crate for reading/writing .plist files if you extend into LaunchAgent management.

Cross-cutting design point worth stating explicitly in your README

"The policy engine and orchestrator have zero OS-specific code. Only the execution engine varies, behind one trait. Adding a fourth platform would mean writing one new impl PrivilegedExecutor, touching nothing else." — this sentence alone signals good architecture to a reviewer skimming your repo.

Recommendation for actually building it: implement fully for one OS first (whichever you dev on daily), stub the other two with clear todo!()/error returns, and if time allows implement a second. Claiming "designed for three platforms, fully implemented on Linux + Windows, macOS stubbed with documented approach" is honest, credible, and still very strong — better than a shallow, buggy three-OS implementation.

5. What the tool can actually do (MVP action catalog)

Keep the MVP catalog small and correct rather than large and shaky:

Action Example NL input Risk tier
Delete files by age/pattern "clean up Downloads older than 90 days" Medium — always dry-run first
Move/organize files "move all PDFs from Downloads to Documents/PDFs" Low
Change file permissions "make this script executable" Low
Kill a runaway process "kill any process using more than 90% CPU for 5+ minutes" Medium
Compress/archive old files "zip up anything in Downloads I haven't touched in a year" Low
Find large files "show me anything over 1GB in my home folder" (read-only — no policy needed) None — good "safe demo" action

Every destructive action supports a dry-run mode by default — the plan is generated and shown, nothing executes until explicit approval, and the UI clearly marks which actions are reversible (move) vs irreversible (delete, kill).

6. Extra features — easy/moderate effort, high visual/technical payoff

Ranked by effort-to-impact ratio for someone at 1–2 YOE building a resume project.

Easy, high impact

  1. Dry-run / simulation mode toggle — show exactly what would happen without doing it. Almost free to build (you already compute estimated_impact), and it's the single best "trust me, I thought about safety" demo moment.
  2. Live execution progress via WebSocket — stream each action's status (pending → running → done/failed) to the UI in real time instead of a spinner-then-result. Turns a static form into a genuinely impressive live demo.
  3. Deliberate "blocked" demo scenario — hardcode a policy rule like "never touch anything outside $HOME" and have a ready demo input that tries to violate it, so you can show the policy engine catching it live. Very cheap to build, extremely persuasive in an interview.
  4. Audit log viewer with filtering — list past plans, who approved them, what executed, success/failure, with a JSON diff view. Reuses UI you're already building for plan review.

Moderate effort, strong payoff

  1. Undo for reversible actions — for MoveFile, store the reverse action in the audit log and offer a one-click undo. For DeleteFile, this means routing deletes through a "trash" staging directory instead of true deletion (soft-delete with a retention window) — a real, defensible safety pattern worth implementing rather than faking.
  2. Confidence/ambiguity handling from the LLM — if the NL request is ambiguous ("clean up my downloads" — by what criteria?), have the LLM return a NeedsClarification response instead of guessing, and have the UI ask a follow-up question. This is a legitimately hard, legitimately good UX problem to solve and shows maturity beyond "happy path only."
  3. Rate limiting / blast-radius caps in the policy engine — e.g., "no single plan may delete more than N files or touch more than X MB without a second explicit confirmation step." Cheap to implement (just a threshold check), reads as genuinely thoughtful safety engineering.
  4. Voice input via Whisper — browser mic capture → Whisper API (or local whisper.cpp if you want zero external dependency) → same NL pipeline as text. Don't build STT yourself; treat it as a clean input adapter. Adds a great demo layer for relatively low integration cost.

Stretch (only if time allows — don't let these block MVP)

  1. Scheduled/recurring plans — "every Sunday, clean up Downloads older than 90 days," with a cron-style scheduler in Rust and a background approval-required or pre-approved-template flow. Interesting because it forces you to think about "who approves an automated recurring privileged action" — a real unsolved-feeling problem, good talking point even if only partially built.
  2. Multi-user / role model — a basic "admin approves plans submitted by standard users" flow. Adds real-world credibility (this is how enterprise automation tools actually work) but is a genuine scope increase — only attempt after MVP is solid.
  3. Plan explainability / reasoning trace — show why the LLM chose those specific actions (e.g., surfacing the function-calling reasoning or a short generated justification per action). Nice-to-have, cheap if your LLM call already supports it, skip if it adds friction.

Recommendation: build items 1–4 as part of your core MVP (they're cheap and they are the safety story), pick 2 of items 5–8 based on what's more interesting to you, and treat 9–11 explicitly as a "Future Work" section in your README rather than something you attempt to finish — a well-written future-work section signals maturity too.

7. Suggested build sequence (2–3 day chunks each)

  1. Action schema + policy engine, unit-tested in isolation with hardcoded Vec<Action> — no LLM, no UI, no real execution yet.
  2. Execution engine for one OS, 3 action types (delete, permission change, kill process), with append-only audit log.
  3. LLM integration: NL → structured ActionPlan via function-calling/JSON mode, tested via CLI/curl only.
  4. React frontend: input box → plan review/diff screen → approve/reject → WebSocket live execution status.
  5. Dry-run mode + blocked-scenario demo + audit log viewer UI.
  6. Pick 2 moderate features (undo, ambiguity handling, blast-radius caps, or voice input).
  7. Second OS backend if time allows; otherwise document the approach clearly and stub it.
  8. Polish + README + a scripted 90-second demo (this matters as much as the code — practice showing: normal request → review → approve → live execution → then a blocked/dangerous request being caught).

8. What to say about it on a resume (draft bullets)

  • Designed and built a natural-language system automation tool with a strict separation between AI planning and privileged execution: an LLM emits a closed, typed action schema which a Rust policy engine validates before a least-privilege execution layer performs any OS-level operation.
  • Implemented cross-platform privileged execution (Windows ACLs/UAC elevation, Linux Polkit/POSIX permissions) behind a single trait, with an append-only audit log and dry-run simulation mode.
  • Built a real-time React frontend streaming live execution status over WebSocket, including plan review/approval UX and a blast-radius safety cap in the policy engine.

9. Explicit non-goals (worth stating, in your repo and to yourself)

  • Not trying to be a general-purpose AI agent framework.
  • Not trying to support arbitrary shell execution — this is a design choice, not a limitation to apologize for.
  • Not aiming for full enterprise RBAC in v1 — single-user, single-machine scope is fine and honest.
  • Not reimplementing Whisper/STT — treat it as an off-the-shelf input adapter.
